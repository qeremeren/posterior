01 / 03Typed decisionsFormulation

A data scientist's judgment calls are typed questions

The model fills slots. Code writes the SQL.

Every judgment call is a choice, or a yes or no.

How it works

The question is split into slots: entity, event, operation, filter, window and population. Each slot becomes one question for a decision model, which answers with a probability for every option. A beam search keeps the most likely complete readings, and a small grammar compiles each one into a RelArena task file and its label SQL.

Why it matters

No model writes SQL, so invalid or invented queries cannot happen by construction. Every decision carries a probability, so uncertainty about the question becomes visible instead of hidden.

Uncertainty about the question, as well as the answer

TabPFN averages over possible datasets. Posterior also averages over possible questions.

How it works

The top readings of the question all run. For each pair, Posterior compares the labels they produce at the same past moments. If the readings select the same entities, it keeps the most likely one. If they disagree, it asks one multiple-choice question about the first slot where they differ.

03 / 03Leakage auditFeature allow-list

Two kinds of evidence, one decision

Perfect on paper usually means it saw the future

A column that predicts too well on its own is probably reporting the outcome.

How it works

For every column, the decision model judges its meaning: was this value known at the moment of prediction, or filled in later? TabPFN measures its behaviour: how well it predicts the label alone, and how much the backtest changes without it. The two are combined into one leakage score, and the column is kept or dropped from the feature allow-list.

Measured

Four snapshot columns computed from the full history were injected into Olist. The meaning prior alone caught 3, TabPFN's lift check alone caught 2, and together they caught all 4 without dropping a single ordinary seller column. On the original columns the audit agrees with Prior Labs' hand-curated allow-list on 88% of them. Without the audit, TabPFN-3.5 scores a perfect 1.000 ROC-AUC on the leaky database; with it, 0.774.

IV

Why both · each covers the other's gap

Meaning decision modelEvidence TabPFN-3.5

Neither model can do this alone. One reads meaning but cannot learn from many examples. The other learns from a million rows but never sees what a column means.

Decision model Jev-style

  • Reads meaning: the question, column names, free text.
  • Returns typed decisions with probabilities in milliseconds.
  • Sees few examples: about 44 rows fit in a 32k-token context.
  • Weak at counting, arithmetic and date comparison.
  • Not calibrated to your data. In Prior Labs' fraud cookbook, Jev predicted 27.5% average risk against a 5% base rate.

TabPFN-3.5 tabular foundation model

  • Learns in context from up to a million rows, with no training.
  • Returns calibrated probabilities and full distributions.
  • Captures numeric relationships and patterns over time.
  • Never sees column names or what they mean.
  • Needs a ready table and a defined target.
  • Cannot tell on its own which columns leak the future.
In one line

One carries the meaning, the other carries the evidence.

What this unlocks
  • Prediction without a data scientist. Anyone who can state the question, or an agent, can ask it.
  • Visible ambiguity. Answering the wrong question well becomes much less likely.
  • Automatic leakage review. Models that only look good on paper are caught before they ship.
  • Local by default. Ollaya and TabPFN-3.5 run on our own GPUs.

Three entry points, one engine

The same result object behind a Python call, an HTTP request and an MCP tool. The HTTP API speaks Jev's wire format, so existing Jev integrations can point at Posterior without code changes.

FormulationRelBench, gold task files

On 11 RelBench tasks, from RelBench's own one-line descriptions, the decision model picks the right answer type and window on all 11 and the right entity on 9. Labels match Prior Labs' hand-written task files exactly on both H&M tasks at the first reading, and on F1 top-3 after one clarification. On the 5 tasks the grammar can state, mean label agreement is 0.67 with one clarification. Tasks that need unions, set filters or two-hop links score low and are listed as future work.

InterfacesTested

23 offline tests. The MCP server answers a real MCP client over stdio with five tools. The HTTP API passes semantic questions through to the decision model and answers future questions from TabPFN, in the same Jev request.

Decision modelsWhat we measured

Atomic questions beat loaded ones, and questions about wording do better with the question alone than with the schema in the state. For "which sellers will stop selling", the stop-or-act answer went from 0.37 (one loaded question with the schema in the state) to 0.89 (an atomic choice on the question alone). Entity choice on RelBench questions went from 4/6 to 6/6 the same way.
